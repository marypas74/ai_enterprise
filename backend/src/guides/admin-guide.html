1. Architettura del Sistema

Panoramica

Enterprise AI Chat e una piattaforma multi-tier distribuita su Kubernetes con i seguenti componenti principali:

                        TLS TERMINATION
                       (HTTPS, WAF, CDN)
                              |
                        NGINX INGRESS
                  (Rate limiting, routing)
                              |
               +--------------+-------------+
               |              |             |
          FRONTEND       BACKEND       WebSocket
         (Nginx+React)  (Fastify 5)   (Real-time)
         2 repliche      2 repliche
               |              |
               +--------------+----------+--------+
                              |          |        |
                          MariaDB     Redis    Ollama
                        (StatefulSet)  (Cache)  (Docker Host)
                              |
                         Parlant
                      (Python Agent, port 8800)

Stack Tecnologico

Frontend
  • React 18 + TypeScript
  • Vite (build tool)
  • Tailwind CSS
  • Zustand (state)
  • React Router v6
  • Axios + SSE
Backend
  • Fastify 5 + TypeScript
  • 20+ moduli
  • MySQL2 (MariaDB)
  • ioredis
  • JWT + bcrypt
  • WebSocket
Infrastruttura
  • MicroK8s
  • Docker
  • Reverse Proxy / CDN
  • Nginx Ingress
  • Node 20 LTS
  • LibreOffice + Tesseract

Flusso delle Richieste

  1. L'utente invia una richiesta HTTPS al dominio della piattaforma
  2. Il Reverse Proxy / CDN termina il TLS e inoltra la richiesta al cluster
  3. Nginx Ingress gestisce il routing: /api/* va al backend, tutto il resto al frontend
  4. Il Backend Fastify autentica via JWT, processa la richiesta e risponde
  5. Per le chat AI, la risposta viene inviata in streaming SSE (Server-Sent Events)
  6. Le sessioni sono gestite tramite Redis, i dati persistenti su MariaDB
Nota sulla Restrizione IP

Quando il sistema e dietro un reverse proxy o tunnel, le annotazioni Kubernetes whitelist-source-range potrebbero non funzionare. La restrizione IP viene gestita a livello applicativo leggendo gli header del proxy (es: X-Forwarded-For, X-Real-IP).

Ollama - Configurazione Speciale

Regole Critiche Ollama
  • Ollama gira come container Docker sull'host, NON in Kubernetes
  • URL base: http://10.0.1.1:8086/ollama (via proxy Antigravity)
  • Header auth: X-Ollama-Key: mTLS-k8s-backend-2026
  • Per pullare modelli: docker exec ollama ollama pull <modello>
  • MAI creare CronJob o pod Kubernetes per Ollama

Il pannello admin Ollama mostra:

  • Stato Docker (running, container ID, porta, GPU)
  • Lista modelli disponibili con dimensione e parametri
  • Pulsante per pullare nuovi modelli
  • Pulsante "Sincronizza da Ollama" per aggiornare la lista

AIProviderFactory

Il servizio AIProviderFactory gestisce la creazione dei client AI per ogni provider. Supporta:

  • Routing automatico - Smistamento richieste al provider/modello selezionato
  • Fallback su quota exceeded - Switch automatico a provider alternativi
  • Conteggio token - Tracciamento per ogni provider
  • Streaming - Supporto SSE per tutti i provider

Tipi di Agente

autonomousAgente autonomoEsecuzione task senza supervisione
tool-callerChiamante di toolEsecuzione sequenziale di tool

Creazione Agente

Ogni agente richiede:

  • Nome e Descrizione
  • Tipo - assistant, autonomous, tool-caller, custom
  • Modello AI - Quale modello usa l'agente
  • System Prompt - Istruzioni per il comportamento
  • Tool - Strumenti a disposizione (selezione multipla)
  • Skill - Competenze abilitate (selezione multipla)
  • Configurazione - Iterazioni massime, timeout

Architettura Orchestratore

L'orchestratore gestisce il ciclo di vita delle sessioni agente:

Componenti dell'Orchestratore
  • AgentOrchestrator - Gestione lifecycle delle sessioni (create, start, pause, resume, cancel)
  • TerminalManager - Pool di 12 slot terminali per esecuzioni parallele
  • WorktreeManager - Isolamento Git worktree per ogni sessione
  • AgentEventEmitter - Streaming eventi in tempo reale (SSE)
  • MCPClientManager - Supporto protocollo MCP per tool esterni

Flusso Sessione Agente

  1. Creazione - L'utente definisce task, modello, configurazione
  2. Inizializzazione - Allocazione slot terminale, creazione worktree (se richiesto)
  3. Esecuzione - L'agente esegue iterazioni: ragionamento → azione → osservazione
  4. Monitoraggio - Log in tempo reale via SSE, metriche aggiornate
  5. Completamento - Merge worktree (se applicabile), rilascio risorse

Gestione Conflitti

Quando un worktree viene mergiato e ci sono conflitti:

  • Il sistema rileva automaticamente i file in conflitto
  • L'AI puo assistere nella risoluzione dei conflitti
  • L'admin puo forzare il merge o annullare
GET /api/orchestrator/status - Stato orchestratore
GET /api/orchestrator/terminals - Stato slot terminali
POST /api/orchestrator/terminals/:slot/release - Rilascio forzato slot
POST /api/orchestrator/worktrees/prune - Pulizia worktree vecchi

8. Memoria e RAG

Pagina Admin: Memoria

Percorso: /admin/memory

Architettura Memoria

4 Livelli di Memoria
  1. Working Memory - Memoria di sessione, volatile, ottimizza i token nella conversazione corrente
  2. Observations (Memoria Testuale) - Osservazioni persistenti per utente (insight, decisioni, pattern, ecc.)
  3. Vector Memory (RAG) - Ricerca semantica su 3 collezioni: episodica, dichiarativa, procedurale
  4. Conversation Summaries - Riassunti delle conversazioni passate, con risparmio token

Servizi di Memoria

ServizioFunzione
MemoryServiceCRUD osservazioni, ricerca full-text
VectorMemoryServiceEmbedding + ricerca semantica
WorkingMemoryServiceGestione contesto sessione
HybridSearchServiceCombinazione full-text + semantica
MemoryDecayServiceDecadimento basato su importanza
HyDEServiceHypothetical Document Embeddings

Pagina Admin: Memoria Vettoriale

Percorso: /admin/vector-memory

Tab Disponibili

  • Collezioni - Vista delle collezioni vettoriali (episodic, declarative, procedural) con conteggio punti e stato
  • Recall - Interfaccia per testare la ricerca semantica: inserisci una query e vedi i risultati raggruppati per collezione con score di similarita
  • Ingest - Ingestione di URL: inserisci un URL, il sistema scarica la pagina, la spezzetta in chunk e la indicizza. Cronologia ingestioni con stato, chunk e errori
  • Settings - Configurazione RAG:
    • Toggle Auto RAG (abilita/disabilita ricerca automatica)
    • Valori K per collezione (quanti risultati restituire)
    • Threshold per collezione (soglia minima di similarita)

Pipeline di Ingestione

  1. URL/documento ricevuto
  2. Estrazione contenuto (scraping, parsing, OCR)
  3. Pulizia e normalizzazione del testo
  4. Chunking (spezzettamento con overlap configurabile)
  5. Generazione embedding vettoriali
  6. Indicizzazione nella collezione appropriata

19. Deploy e Infrastruttura

Build

cd enterprise-ai-chat
bash BUILD.sh    # Richiede sudo: npm install, Docker build, MicroK8s import, K8s deploy

Cosa fa BUILD.sh

  1. npm install per backend e frontend
  2. Build TypeScript del backend
  3. Build Vite del frontend
  4. Build Docker images (multi-stage)
  5. Push al registry locale localhost:32000/
  6. Apply manifesti Kubernetes

Docker Images

  • Backend - Node 20 builder → production. Include LibreOffice, Poppler, Tesseract, fonts
  • Frontend - Node 20 builder → Nginx Alpine. Gzip, security headers, streaming support

Deploy Rapido

sudo bash DEPLOY.sh    # Import tar pre-built e restart K8s deployments

Rollout

Procedura di Rollout Obbligatoria
  1. Scala repliche a 0: kubectl scale deployment backend --replicas=0
  2. Applica il nuovo deployment
  3. Ripristina repliche originali: Backend 2, Frontend 2, LiteLLM 1

Regole Critiche Deploy

MAI Fare
  • MAI usare kubectl apply -k se k8s/secrets.yaml ha valori placeholder - sovrascrive i segreti reali
  • MAI usare commonLabels in kustomization.yaml - rompe i selectors dei Service
  • MAI creare CronJob/pod K8s per Ollama - gira come Docker container sull'host

20. Troubleshooting

Pod non si avviano

Verifica: kubectl describe pod <nome> -n enterprise-ai-chat. Cause comuni: immagine non trovata nel registry locale, segreti mancanti, risorse insufficienti.

Errore 502 Bad Gateway

Il backend non risponde. Verifica i log: kubectl logs deployment/backend -n enterprise-ai-chat. Cause comuni: errore nella connessione al database, variabili d'ambiente mancanti.

Ollama non risponde

Verifica che il container Docker sia attivo: docker ps | grep ollama. Verifica il proxy: curl http://10.0.1.1:8086/ollama/api/tags -H "X-Ollama-Key: mTLS-k8s-backend-2026"

Segreti sovrascritti

Se i segreti sono stati accidentalmente sovrascritti da kubectl apply -k, ricreali manualmente: kubectl create secret generic enterprise-ai-chat-secrets --from-literal=KEY=VALUE -n enterprise-ai-chat

Redirect loop con reverse proxy

Se il sistema e dietro un reverse proxy che gestisce TLS, assicurati che ssl-redirect sia impostato a "false" nell'Ingress. Il doppio redirect SSL causa loop infiniti.

Frontend non si build

Usa --legacy-peer-deps per npm ci nel Dockerfile frontend. Verifica che il Dockerfile contenga il flag.

Memoria vettoriale vuota

Verifica che il servizio di embedding sia attivo e che le collezioni siano state inizializzate. Controlla la pagina /admin/vector-memory per lo stato delle collezioni.

Appendice B: Sistema di Hooks Avanzato

Il sistema di hooks implementa un pattern event-driven che permette ai plugin di intercettare, trasformare e reagire a eventi durante l'intero ciclo di vita delle richieste.

Meccanismo di Concatenamento (Hook Chaining)

Quando piu handler sono registrati sullo stesso hook, vengono eseguiti in catena secondo la priorita:

Flusso di Esecuzione
  1. L'evento viene emesso con un dato iniziale
  2. L'handler con priorita piu alta viene eseguito per primo
  3. L'output dell'handler N diventa l'input dell'handler N+1
  4. Il risultato finale viene restituito al sistema

Hook Personalizzati (Inter-Plugin)

I plugin possono definire e emettere hook personalizzati per la comunicazione inter-plugin:

  • Un plugin emette un hook con dati iniziali
  • Altri plugin ascoltano e possono trasformare i dati
  • Il risultato finale viene restituito al plugin emittente
Best Practice

Usare hook personalizzati per disaccoppiare la logica tra plugin correlati, consentendo estensioni future senza modificare il codice esistente.

Appendice C: Configurazione Tools AI

I tool sono funzioni che l'LLM puo decidere autonomamente di invocare durante una conversazione. Il modello legge la descrizione del tool e sceglie quando e come utilizzarlo.

Ciclo di Decisione LLM

Come l'LLM Seleziona i Tool
  1. L'utente invia un messaggio
  2. I tool disponibili vengono recuperati dalla memoria procedurale tramite ricerca semantica
  3. Le descrizioni dei tool vengono passate all'LLM come contesto
  4. L'LLM decide se usare un tool e con quali argomenti
  5. Il framework esegue il tool selezionato
  6. Il risultato viene restituito direttamente all'utente o rielaborato dall'agente

Proprieta dei Tool

ProprietaTipoDescrizione
NomestringIdentificativo univoco del tool
DescrizionestringDescrizione per l'LLM (CRITICA: determina quando il tool viene scelto)
Schema InputJSON SchemaDefinizione dei parametri di ingresso
Richiede ApprovazionebooleanSe abilitato, l'utente deve confermare prima dell'esecuzione
Return DirectbooleanSe vero, l'output va direttamente all'utente senza rielaborazione LLM
Esempistring[]Frasi di trigger che aiutano la ricerca semantica
Sicurezza Tool

I tool con Richiede Approvazione disabilitato vengono eseguiti automaticamente senza conferma dell'utente. Abilitare sempre l'approvazione per tool che eseguono azioni irreversibili (scrittura file, invio email, modifiche database).

Chain del Tool nell'Agente

L'agente AI utilizza un sistema a doppia catena per decidere come rispondere:

Procedures Chain

Attivata quando tool rilevanti vengono trovati nella memoria procedurale. L'LLM seleziona ed esegue i tool appropriati.

Memory Chain

Attivata quando nessun tool e applicabile. Genera risposte usando la memoria dichiarativa (documenti) ed episodica (conversazioni passate).

Appendice E: Architettura della Memoria

Il sistema di memoria implementa un'architettura a 4 livelli ispirata alla cognizione umana, con memoria a lungo termine persistente e memoria di lavoro volatile.

Memoria a Lungo Termine (Vettoriale)

Archiviata nel database vettoriale (Qdrant), sopravvive ai riavvii del sistema ed e organizzata in tre collezioni semantiche:

Episodica

Cosa: Contesto delle conversazioni passate

Sorgente: Interazioni utente automaticamente indicizzate

Uso: Ricordare discussioni precedenti, preferenze espresse, contesto storico

Dichiarativa

Cosa: Conoscenza fattuale e documentale

Sorgente: Documenti caricati (PDF, DOCX, URL)

Uso: RAG - risposte basate su documenti aziendali

Procedurale

Cosa: Tool, skill e procedure operative

Sorgente: Definizioni di plugin e tool

Uso: Selezione automatica degli strumenti appropriati

Pipeline di Ricerca Semantica

  1. Il messaggio dell'utente viene convertito in un vettore di embedding
  2. Il vettore viene confrontato con tutti i vettori nelle tre collezioni
  3. I risultati piu simili (sopra la soglia configurata) vengono restituiti
  4. I risultati vengono iniettati nel contesto dell'LLM come informazione aggiuntiva
  5. L'LLM genera la risposta tenendo conto del contesto recuperato

Configurazione Recall

ParametroPer CollezioneDescrizione
K (risultati)SiNumero massimo di risultati da restituire per collezione
Threshold (soglia)SiSimilarita minima (0.0-1.0) per includere un risultato
Auto RAGGlobaleAbilita/disabilita la ricerca automatica ad ogni messaggio

Memoria di Lavoro (Working Memory)

Memoria volatile di sessione che mantiene il contesto della conversazione corrente:

Proprieta della Working Memory
ProprietaDescrizione
historyCronologia interazioni della sessione
user_messageMessaggio utente corrente
active_formForm conversazionale attivo (se presente)
recall_queryQuery usata per il richiamo memoria
episodic_memoriesMemorie episodiche recuperate

La working memory puo essere estesa con attributi personalizzati per mantenere stato tra una chiamata e l'altra all'interno della stessa sessione (es: contatori, stati di una macchina a stati, dati temporanei).

HyDE (Hypothetical Document Embeddings)

Tecnica avanzata per migliorare la qualita della ricerca semantica:

  1. L'LLM genera un documento ipotetico che risponderebbe alla query dell'utente
  2. Il documento ipotetico viene convertito in embedding
  3. La ricerca vettoriale viene eseguita con l'embedding del documento ipotetico
  4. Questo produce risultati piu rilevanti rispetto alla semplice ricerca con la query originale

Appendice F: Pipeline di Ingestione Avanzata

La pipeline di ingestione (Rabbit Hole) gestisce il caricamento, la processazione e l'indicizzazione dei documenti nella memoria dichiarativa.

Formati Supportati e Parser

FormatoParserNote
PDFpdf-parse + OCR (Tesseract)Supporta PDF nativi e scansionati
DOCXMammothEstrazione testo con struttura
XLSXXLSX parserDati tabulari convertiti in testo
PPTXPPTXGenJSTesto slide per slide
TXT / MDLettura direttaNessuna conversione necessaria
HTML (URL)Web scraper + TrafilaturaEstrazione contenuto principale, rimozione nav/footer
ImmaginiTesseract OCRPNG, JPG, GIF, WebP

Fasi della Pipeline

Flusso Completo di Ingestione
  1. Ricezione - File caricato o URL inviato (con protezione SSRF per URL)
  2. Parsing - Estrazione testo dal formato originale (hook: instantiates_parsers)
  3. Pre-Processing - Pulizia testo, rimozione rumore (hook: before_splits_text)
  4. Chunking - Segmentazione in frammenti con overlap (hook: instantiates_splitter)
    • Chunk Size - Dimensione target di ogni frammento
    • Chunk Overlap - Sovrapposizione tra frammenti consecutivi per mantenere contesto
  5. Post-Chunking - Filtraggio/arricchimento chunk (hook: after_splitted_text)
  6. Embedding - Conversione di ogni chunk in vettore numerico tramite il modello di embedding configurato
  7. Pre-Storage - Aggiunta metadata (hook: before_stores_documents)
  8. Indicizzazione - Inserimento nel database vettoriale (collezione dichiarativa)
  9. Post-Storage - Notifiche, trigger secondari (hook: after_stored_documents)

Personalizzazione della Pipeline

Ogni fase della pipeline puo essere personalizzata tramite hook:

Esempi di Personalizzazione
  • Aggiunta parser - Supporto per formati non standard (es: file CAD, formati proprietari)
  • Chunk size adattivo - Dimensione variabile basata sul tipo di contenuto
  • Filtraggio contenuto - Rimozione sezioni irrilevanti (indici, note legali ripetitive)
  • Metadata personalizzati - Aggiunta di tag, categorie, data di validita ai chunk
  • Notifiche - Invio email/webhook al completamento dell'ingestione

Protezione SSRF

L'ingestione di URL include protezione SSRF (Server-Side Request Forgery) che blocca automaticamente:

  • URL verso indirizzi IP privati (10.x.x.x, 172.16-31.x.x, 192.168.x.x)
  • URL verso localhost e loopback (127.0.0.1, ::1)
  • URL verso reti interne del cluster

Appendice H: Autenticazione e Autorizzazione Avanzata

Metodi di Autenticazione

JWT (JSON Web Token)
  • Token con scadenza configurabile
  • Session ID embedded nel token
  • Refresh token via HTTP-only cookie
  • Rotazione automatica dei token
  • Revoca su nuovo login (sessione singola)
API Key
  • Header: Authorization: Bearer <API_KEY>
  • Accesso completo a tutte le risorse
  • Ideale per integrazioni M2M
  • Nessuna scadenza (revocabile manualmente)

Autorizzazione (RBAC)

Il sistema implementa un modello di autorizzazione Role-Based Access Control con permessi granulari:

PermessoScopeDescrizione
READPer risorsaVisualizzazione dati
WRITEPer risorsaCreazione e modifica
DELETEPer risorsaEliminazione
LISTPer risorsaElenco risorse
ADMINGlobaleOperazioni amministrative

Tipi di Utente

TipoDescrizioneAuth Method
InternoCreato nel sistema, credenziali localiEmail + password + MFA opzionale
APIAccesso programmaticoAPI Key
EsternoIntegrato tramite auth handler customOAuth, SAML, LDAP (via plugin)

Auth Handler Personalizzati

Il sistema supporta handler di autenticazione personalizzati tramite il sistema plugin, consentendo l'integrazione con identity provider esterni (Active Directory, Okta, Auth0, ecc.):

  • Implementare le interfacce di validazione JWT e API key
  • Registrare l'handler tramite l'hook factory_allowed_auth_handlers
  • Configurare le credenziali del provider esterno nelle impostazioni del plugin

Best Practice di Sicurezza

Checklist Sicurezza
  • Impostare sempre un JWT secret forte e casuale (mai usare il valore di default)
  • Configurare rate limiting sugli endpoint di login
  • Abilitare MFA per tutti gli account admin
  • Usare HTTPS in produzione (mai HTTP)
  • Gli endpoint custom dei plugin sono aperti per default - aggiungere sempre il controllo permessi
  • Verificare la lista /admin/sessions regolarmente per sessioni sospette
  • Ruotare le API key periodicamente
